## 一、存储位置

| 内容 | 路径 |
|------|------|
| 唯一真相源 | `$DSH_HOME/lifegame/db.json` |
| 收藏的图片 | `$DSH_HOME/lifegame/media/<id>.<ext>` |
| 面板 / API | `/lifegame/*`（state / op / media） |

**原则**：db.json 说了算，客户端不缓存真相；每个写操作带 `opId`，重复提交不重复计数；日期由客户端给（用户本地时区）。

## 二、顶层结构（db.json）

```
{
  rev         : int          // 每次写入 +1，客户端据此判断是否要重渲染
  appliedOps  : [{opId, op, at}]   // 幂等去重表（⚠ 无上限，见 §五）
  profile     : {...}        // 我：偏好、目标、每天的规矩、收集仓库
  season      : {...}        // 当前"季"（如「降噪季 4/14」）
  days        : {"YYYY-MM-DD": Day}    // 每天
  weeks       : {"YYYY-MM-DD": Week}   // 每周（key = 那周周一）
  readlater   : [...]
  weather     : {...}        // 缓存，每小时拉一次
  corpus      : []           // 已废弃（保留空数组给旧引用兜底）
}
```

## 三、四个核心实体

### 1. `profile` — 「我」

```
profile = {
  sleepTarget, meditationMinutes, moveMinutes,
  budget, fitnessLevel,
  location: { name, lat, lon },          // 杭州 · 余杭
  customPlan  : {meditate, move, create} // 每天的规矩：标题模板
  customSlots : {meditate, move, create} // 每天的规矩：时间模板
  goals: { short: [Goal], long: [Goal] },
  collect: { book[], movie[], article[], image[], skill[] }
}
```

- **customPlan / customSlots** 只在用户改过时才有 key；`defaultPlan()` 有就优先用
- **Goal** = `{ id, text, done, steps: [{id, text, done, placed}] }`
- **collect 条目** = `{ id, title, note, url, done, at }`（image 的 `url` 指向 `/lifegame/media?name=...`）

### 2. `days` — 每天

```
Day = {
  date, sleptAt, wokeAt, intention,
  plan: [PlanItem],        // 规定事项（三条地基）
  after: [{time, title}],  // 之后（到点会提醒）
  todos: [Todo],           // 今天要做（自由待办）
  sessions: [{id, seconds, label, startedAt, endedAt}],  // 专注记录
  timer: {label, minutes, startedAt} | null,             // 正在跑的番茄
  inspiration: {text, from, at},                         // 每日灵感
  alt, teaser, watching: []                              // 或者 / 推荐去 / 它在看着
}
```

- **PlanItem** = `{ id: meditate|move|create, title, kind, minutes, slot, done, doneAt }`
- **Todo** = `{ id, text, done, at, fromInbox?, fromNote?, fromRec?, fromRead?, minutes? }`
  - `from*` 是**溯源字段**：这条待办是从哪来的，决定它跟着谁变

### 3. `weeks` — 每周

```
Week = {
  key,                     // 那周的周一
  inbox: [InboxItem],      // 本周待办（可排期到某天）
  notes: [Note],           // 便签（只属于这周）
  recommend: {items: [Rec], at, source},  // 本周推荐
  comment: null            // 已废弃（「这周的话」删了）
}
```

- **InboxItem** = `{ id, text, done, date, fromStep?, fromGoal?, at }`
- **Note** = `{ id, text, color, at }`
- **Rec** = `{ id, kind: book|movie|wear|read|out|rest, title, why, minutes, placed? }`

### 4. `readlater` — 稍后深度阅读

```
ReadlaterItem = {
  id, url, title,
  status: pending|parsing|ready|failed|done,
  summary, outline: [], minutes, placed?
}
```

## 四、Entity 关系

```
profile.goals ──(拆解)──> Goal.steps ──(放到本周)──> weeks.inbox ──(排期)──> days.todos
                                                        │
profile.collect ──(推荐依据)──> weeks.recommend ──(安排)──> days.todos
                                                        │
readlater ──(拖拽/加进今天)───────────────────────────> days.todos
```

**关键约束：`days.todos` 是唯一的汇合点。** 来自四个源头的条目都在这里汇合，靠 `fromInbox / fromNote / fromRec / fromRead` 区分来源，所以：
- 「排进去」和「当天呈现」永远是同一份数据
- 改文字 / 勾完成 / 删除，源头跟着动

`days.todos` 的顺序 = 用户拖拽出来的顺序（`reorder` op 直接动数组）。

### 9.3 走查中发现并修掉的一个真 bug

**错误信息撒谎**：原来 `applyOp` 返回 `false`（业务校验失败）和「没有这个 op」都报同一句话 `unknown op: xxx`。

后果：
- 用户传了非法参数，界面提示「插件宿主还没重启」——完全错误的指引
- 我上一轮自己就被它误导，以为 op 丢了

修法：`applyOp` 的 `default` 分支返回 `"UNKNOWN_OP"` 哨兵值，handler 区分：

```
UNKNOWN_OP  → 404 unknown op: xxx
false       → 400 op 没生效：xxx（参数可能不合法，或目标不存在）
```

前端据此给不同提示（前者才说「宿主没重启」）。

## 十、发布记录

### 10.1 npm 首发的两个坑

**坑一：registry 是镜像**

本机 `~/.npmrc` 配的是 `registry.npmmirror.com`（淘宝镜像），**镜像不能发布**。必须显式加 `--registry=https://registry.npmjs.org`，否则会静默失败或报莫名其妙的错。

**坑二：2FA 拦发布**

```
403 Two-factor authentication or granular access token with bypass 2fa is required
```

账号开了两步验证，`npm publish` 必须出示 OTP。两条路：

- `npm publish --otp=<六位码>`：30 秒过期，来回一趟容易来不及
- **建 granular access token 并勾 "Bypass 2FA"**：一次配好，长期省事 ← 用了这个

token 写进 `~/.npmrc` 的 `//registry.npmjs.org/:_authToken=`。

**坑三（最吓人的一个）：`0.0.0-stage` 占位符**

首次发布后，registry 上出现的不是 `1.0.0`，而是一个叫 `0.0.0-stage` 的版本：

```
version: 0.0.0-stage
description: Temporary package placeholder for staged publishing
```

一度以为是包名被抢或者发错了。查 [npm 文档](https://docs.npmjs.com/staged-publishing/) 才明白：

> 全新包的首次发布，npm 会先放一个 `0.0.0-stage` 占位符，等处理完（约 1–2 分钟）才把真版本放上去。
> **这不是 staged publishing，`npm stage list` 是空的，没有东西要批准。**

`npm publish` 返回的 `202 Accepted` 就是这个意思——**已接收，正在处理**。

等待 1–2 分钟后：

```
dist-tags: {'latest': '1.0.0'}
versions: ['0.0.0-stage', '1.0.0']
```

**教训**：看到 `202` 不要立刻断言失败。先等，再用 registry 的原始 JSON 查（`curl https://registry.npmjs.org/<name>`），`npm view` 有缓存会读到旧的。

### 10.4 1.0.1：engines 写错导致装不上

**症状**：用户装 1.0.0 时提示

> dsh-lifegame@1.0.0 与 DSH 0.2.2-rc.5 不兼容（要求 engines.dsh >=0.2.2）

**原因**：我加 `engines.dsh: ">=0.2.2"` 时没想预发布版本。按 semver 规则：

```
0.2.2-rc.5  <  0.2.2
```

预发布版本**小于**对应正式版。所以 `0.2.2-rc.5` 不满足 `>=0.2.2`，被 DSH 的兼容性检查拒了。

**修法**：`>=0.2.2-0`。`-0` 是 semver 的惯用写法，表示"包含所有 0.2.2 的预发布版本"：

| DSH 版本 | `>=0.2.2` | `>=0.2.2-0` |
|----------|-----------|-------------|
| 0.2.1 | ✗ | ✗ |
| 0.2.2-rc.5 | ✗（就这里出事） | ✓ |
| 0.2.2 | ✓ | ✓ |
| 0.2.3 | ✓ | ✓ |

**教训**：写 `engines` 时如果目标是"从这个版本起"，而该版本还在 rc/beta 阶段，必须带 `-0` 后缀。否则所有还在预发布渠道的用户都装不上——而这批人往往正是最早试用的人。

已发 1.0.1，1.0.0 标记为 deprecated。


### 10.5 1.0.2：两个统计口径的错

生成示例数据截图时发现：显示「第 16 天 · 连续 16 天 · 活跃 16/16」，但点阵上明明有断档。

查出来 `computeStats` 两处口径错了。

**错一：`streak` 按记录列表算，不按日历算**

```js
// 错：keys 是「有记录的日期」数组，中间断掉的那天如果没建 day 对象，就被跳过了
for (const k of keys) {
  if (isActive(db.days[k])) run += 1;
  else run = 0;
}
out.streak = run;
```

后果：断开一周再回来，它还说「连续 N 天」。这种数字是骗人的，而且骗的是最需要准确反馈的那个指标。

改：从今天往前逐个日历日期查，缺一天就断。

```js
const cursor = new Date();
if (!activeOn(ymd(cursor))) cursor.setDate(cursor.getDate() - 1);  // 今天还没开始，从昨天算
while (activeOn(ymd(cursor))) { calStreak += 1; cursor.setDate(cursor.getDate() - 1); }
```

`longestStreak` 同理，改成从第一条记录那天走到今天，逐天查。

**错二：「第 N 天」用了记录条数**

```js
days: keys.length   // 错：有几天记录就是第几天
```

后果：中间跳过几天就少算，数字会莫名其妙变小。

改：从第一条记录到今天的日历跨度。

**修好之后**

| | 修前 | 修后 |
|---|---|---|
| 第 N 天 | 16 | 25 |
| 活跃 | 16/16（100%） | 18/25（72%） |
| 连续 | 16 天 | 3 天 |
| 最长 | 16 天 | 6 天 |

修后的数字和点阵上看得见的断档**对得上**了。这是判断统计有没有写错的最好办法：**看图和数字是否一致**。

顺带调了示例数据的断档规则（显式跳过 7 天，中间留一段 6 天连续），让「连续 3 天 / 最长 6 天」看起来像个真人在用。
