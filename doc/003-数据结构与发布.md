# 数据结构与发布清单

> 最后更新：2026-11-26（v49）

---

## 一、存储位置

| 内容 | 路径 |
|------|------|
| 唯一真相源 | `$DSH_HOME/lifegame/db.json` |
| 收藏的图片 | `$DSH_HOME/lifegame/media/<id>.<ext>` |
| 面板 / API | `/lifegame/*`（state / op / media） |

**原则**：db.json 说了算，客户端不缓存真相；每个写操作带 `opId`，重复提交不重复计数；日期由客户端给（用户本地时区）。

---

## 二、顶层结构（db.json）

```
{
  rev         : int          // 每次写入 +1，客户端据此判断是否要重渲染
  appliedOps  : [{opId, op, at}]   // 幂等去重表（⚠ 无上限，见 §五）
  profile     : {...}        // 我：偏好、目标、每天的规矩、收集仓库
  season      : {...}        // 当前"季"（如「降噪季 4/14」）
  days        : {"YYYY-MM-DD": Day}    // 每天
  weeks       : {"YYYY-MM-DD": Week}   // 每周（key = 那周周一）
  readlater   : [...]
  weather     : {...}        // 缓存，每小时拉一次
  corpus      : []           // 已废弃（保留空数组给旧引用兜底）
}
```

## 三、四个核心实体

### 1. `profile` — 「我」

```
profile = {
  sleepTarget, meditationMinutes, moveMinutes,
  budget, fitnessLevel,
  location: { name, lat, lon },          // 杭州 · 余杭
  customPlan  : {meditate, move, create} // 每天的规矩：标题模板
  customSlots : {meditate, move, create} // 每天的规矩：时间模板
  goals: { short: [Goal], long: [Goal] },
  collect: { book[], movie[], article[], image[], skill[] }
}
```

- **customPlan / customSlots** 只在用户改过时才有 key；`defaultPlan()` 有就优先用
- **Goal** = `{ id, text, done, steps: [{id, text, done, placed}] }`
- **collect 条目** = `{ id, title, note, url, done, at }`（image 的 `url` 指向 `/lifegame/media?name=...`）

### 2. `days` — 每天

```
Day = {
  date, sleptAt, wokeAt, intention,
  plan: [PlanItem],        // 规定事项（三条地基）
  after: [{time, title}],  // 之后（到点会提醒）
  todos: [Todo],           // 今天要做（自由待办）
  sessions: [{id, seconds, label, startedAt, endedAt}],  // 专注记录
  timer: {label, minutes, startedAt} | null,             // 正在跑的番茄
  inspiration: {text, from, at},                         // 每日灵感
  alt, teaser, watching: []                              // 或者 / 推荐去 / 它在看着
}
```

- **PlanItem** = `{ id: meditate|move|create, title, kind, minutes, slot, done, doneAt }`
- **Todo** = `{ id, text, done, at, fromInbox?, fromNote?, fromRec?, fromRead?, minutes? }`
  - `from*` 是**溯源字段**：这条待办是从哪来的，决定它跟着谁变

### 3. `weeks` — 每周

```
Week = {
  key,                     // 那周的周一
  inbox: [InboxItem],      // 本周待办（可排期到某天）
  notes: [Note],           // 便签（只属于这周）
  recommend: {items: [Rec], at, source},  // 本周推荐
  comment: null            // 已废弃（「这周的话」删了）
}
```

- **InboxItem** = `{ id, text, done, date, fromStep?, fromGoal?, at }`
- **Note** = `{ id, text, color, at }`
- **Rec** = `{ id, kind: book|movie|wear|read|out|rest, title, why, minutes, placed? }`

### 4. `readlater` — 稍后深度阅读

```
ReadlaterItem = {
  id, url, title,
  status: pending|parsing|ready|failed|done,
  summary, outline: [], minutes, placed?
}
```

## 四、Entity 关系

```
profile.goals ──(拆解)──> Goal.steps ──(放到本周)──> weeks.inbox ──(排期)──> days.todos
                                                        │
profile.collect ──(推荐依据)──> weeks.recommend ──(安排)──> days.todos
                                                        │
readlater ──(拖拽/加进今天)───────────────────────────> days.todos
```

**关键约束：`days.todos` 是唯一的汇合点。** 来自四个源头的条目都在这里汇合，靠 `fromInbox / fromNote / fromRec / fromRead` 区分来源，所以：
- 「排进去」和「当天呈现」永远是同一份数据
- 改文字 / 勾完成 / 删除，源头跟着动

`days.todos` 的顺序 = 用户拖拽出来的顺序（`reorder` op 直接动数组）。

## 五、当前的已知问题（发布前要处理）

| # | 问题 | 影响 |
|---|------|------|
| 1 | `appliedOps` **无上限** | 每条 op 都存一条，220 条/3 天。跑一年会到几万条，db.json 持续膨胀 |
| 2 | **icon.svg 是旧配色**（黑底 + 金色） | 与现在的极简白完全不符，发布后第一印象就错 |
| 3 | `lifegame_corpus` 工具还在 | 语料库功能已删，工具还暴露着——Agent 会去用一个空功能 |
| 4 | `corpus` 空数组还在 db 里 | 无害，但发布前该清掉 |
| 5 | 包名 `@local/lifegame` + `private: true` | 不能直接发布到 npm |
| 6 | 无 locale / docs / README | Plugin Manager 里会显示裸包名和默认图标 |
| 7 | 无数据迁移版本号 | db 结构改过 6 次，都靠 `load()` 里的隐式迁移。发布后别人升级会踩坑 |
| 8 | 无备份 / 恢复 | db.json 一坏，用户所有记录没了 |

## 六、发布清单

### A. 阻断项（不做不能发）

| # | 事项 | 具体动作 | 预估 |
|---|------|---------|------|
| A1 | **包标识** | `name` 改成可发布的（如 `dsh-lifegame`），去掉 `private: true`，`version` 走 semver | 10 分钟 |
| A2 | **locale** | `locale/en.json` + `locale/zh.json`：`meta.title` / `meta.description`（说清功能、怎么打开、有什么限制） | 40 分钟 |
| A3 | **icon** | 重画：极简白风格，用一个可辨识的符号（不是太阳/表盘这种通用图标） | 40 分钟 |
| A4 | **详情页图** | `docs/preview.svg`（640×300，单图）+ `docs/DETAIL.zh.md` / `DETAIL.md`（各一行图 + alt） | 40 分钟 |
| A5 | **exports / files** | 加 `"./locale/*.json"`、`"./icon"`；`files` 加 `locale`、`docs` | 10 分钟 |
| A6 | **清理废弃物** | 删 `lifegame_corpus` 工具、删 `db.corpus` 字段 | 20 分钟 |
| A7 | **appliedOps 封顶** | 只保留最近 500 条（`slice(-500)`），或改用「时间窗口」去重 | 20 分钟 |

### B. 稳定性（发了不会立刻炸，但迟早出事）

| # | 事项 | 说明 |
|---|------|------|
| B1 | **数据版本号 + 迁移** | `db.schemaVersion`，`load()` 里按版本逐级迁移。现在的隐式迁移（`if (!Array.isArray(...))`）能应付，但无法回溯 |
| B2 | **自动备份** | 每次 `persist()` 前把上一版复制成 `db.bak.json`（只留一份，够救命） |
| B3 | **错误边界** | 面板 `LifegamePanel` 外层加 React error boundary：某一屏崩了，至少还能看到提示而不是白屏 |
| B4 | **离线 / 慢网络** | `sendOp` 现在失败就弹红条。可以加简单重试（1 次）+ 离线时禁用按钮 |
| B5 | **LLM 不可用降级** | 推荐 / 拆解 / 灵感都依赖 `ctx.llm`。没有模型时要有明确文案，而不是静默失败 |

### C. 合规与说明（别人用之前必须知道）

| # | 事项 | 说明 |
|---|------|------|
| C1 | **数据在哪** | `meta.description` 里写明：数据只存本地 `$DSH_HOME/lifegame/`，不上传 |
| C2 | **会读什么** | 位置（用于天气）、本机时间；写清可以在设置里改 |
| C3 | **会调模型** | 推荐 / 拆解 / 灵感会调 LLM，说明调用频率（推荐手动触发、灵感每天 1 次、拆解手动） |
| C4 | **图片存储** | 收藏的图片落盘到 `media/`，单张 ≤ 8MB，写明 |

### D. 可选（不影响可用性，影响专业度）

| # | 事项 | 说明 |
|---|------|------|
| D1 | README | 面向使用者：装上之后在哪找到它、第一次用做什么 |
| D2 | 截图 | 真实界面的三张（今天 / 本周 / 我） |
| D3 | dshGo 原生插槽 | 手机端体验，目前只有 Web |
| D4 | 测试 | 至少 `check-ops.mjs` 进 CI；op 的回归测试可以后补 |

## 七、发布路径（三选一）

| 路径 | 适合 | 步骤 |
|------|------|------|
| **本地目录安装** | 只给自己 / 朋友用 | 当前 `plugin/` 目录直接用 `plugin_manager install_bundle` 链过去，改代码即生效 |
| **tgz 分发** | 发给少数人 | `npm pack` → 对方 `plugin_manager install_bundle <tgz>` |
| **npm 发布** | 公开 | 需要 npm 账号 + 包名可用；发布后 `dsh plugin install <name>` |

**建议先走第二条**：`npm pack` 出一个 tgz，自己在另一台机器上装一遍——这一步会暴露所有 `files` 漏配、locale 缺文件、icon 不渲染的问题，比直接发 npm 便宜。

## 八、我发现的最重要的一件事

**这个插件现在有 10 个工具、57 个 op、5 个页面区域，但零测试。**

发布意味着"别人用"，别人会遇到我没走过的路径：
- 收藏仓库第一次为空
- 目标拆解时模型返回了非 JSON
- 番茄在跨天时还在跑
- 把 Inbox 的一条拖到下周（`weeks` 换 key）

这些我都**没验证过**。发布前至少要做一轮"空数据 + 乱序操作"的手动走查。
